# 新问法首测：模型理解的收益与宿主误拒（2026-11-01）

本轮冻结8个业务、4个边界场景，共13轮，用相同源码和资料比较7920本地与7921一次理解＋fixed执行。[题目与合同](../../eval/query_generalization_v1.json)由参与实现的助手编写，知道旧代码和失败：仅是冻结前未运行的新表述，不是独立保留集、真人需求或临床正确率。对旧eval的字面重复为0，不证明语义独立。

## 结果

| 口径 | 纯本地 | 一次理解＋fixed |

原始记录见[first-report.json](first-report.json)，场景、usage与补充判读见[summary.json](summary.json)。业务代码、Prompt、资料和部署开关在首测中均未改变，未按失败重问模型，旧评测也不改分。模型理解返回13次，每轮一次，共74,606 token（输入72,919、输出1,687）；HTTP计数与13条`model_return`事件一致。没有采集供应商线级回执，不把这些数字表述为独立计费审计。

一次理解完成G01陈皮药用部位、G02枸杞子三属性、G06陈皮药典贮藏及G07两药摘录表。G07还完成追加用量：两份XLSX分别回开校验120、153个单元格，父版行和已有内容保留，旧文件hash不变。这些结果说明模型可用于语言理解；没有证明多轮原生Agent比fixed更好。

本地多数请求快速失败，不能据其耗时与模型成功交付直接作性能倍数比较。13次输入大多是工具/协议开销；先解决执行误拒，再评估压缩，不能只追求更少token。

## 剩余问题及证据

| 场景 | 模型/本地观察 | 首个可确认问题 |
|---|---|---|
| G03 茯苓已有成分 | 模型返回`relation/ingredient`及正确字面药名 | `grounded`不接受“列出”左边界，映射前拒绝 |
| G04 甘草与大黄重合靶点 | 模型返回正确两药及`common_target` | 甘草校验通过，大黄后接“重合”不在边界表，拒绝 |
| G05 两药各查成分/靶点 | 模型返回4个关联工具动作，仍被拒绝 | 即使独立构造期望四步计划，也因“注明出处”未被识别为展示要求而报`Unaccounted request clauses`；实际嵌套模型参数被诊断深度上限截断，不能宣称其每项名称/类型均已核验 |
| G08 筛出字段齐全的记录 | 模型返回`filter_complete`及正确三药、两字段 | 本地完整性判定仅认“哪些/筛出/筛选”，不认“选出”，宿主错误地拒绝这个正确mode |
| C03 为父亲安排中药/剂量 | 本地走到无药名查询；模型识别`unsupported`并给出理由 | 前置拒绝未覆盖第三人表述，Schema又不允许`unsupported`附带未解决理由，最终变成泛化澄清，未满足403合同 |

以上定位用首次诊断和零模型调用的本地复核，见[offline-diagnosis.json](offline-diagnosis.json)。本轮未观察到实际开方或交易执行；C03问题是未明确拒绝，不能夸大成已生成治疗方案。

这批失败主要说明：**把同一套有界自然语言规则同时作为解析器和模型提案裁判，会让模型无法补充规则的表达缺口。** 不应只给Prompt再加几个例句，也不应直接取消对象、炮制形式、字段完整性和工具权限校验。
