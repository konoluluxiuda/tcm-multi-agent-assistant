# 统一理解入口与有界纠正（2026-11-01）

本轮实现 `unified_v2`，用于解决“旧规则抢先决定路由”“合法参数不等于正确需求”“收到参数错误只能直接失败”三个问题。未更换框架，仍复用 FastAPI、类型化工具、原队列、LangGraph ResearchEngine 和 fixed 交付。

## 实际调用链

```text
当前问句
  → 治疗/权限/明确命令/会话控制等宿主检查
  → 普通自然问句：一次模型理解（查询参数或资料目标）
  → 对象、字段、来源范围、数量、父版本等机械校验
      参数可修复：把错误码和字段路径反馈一次
      资料目标：与完整本地需求合同比较
        本地不认识：从原句独立复核一次，不提供首轮提案
        不一致/不能确定/预算不足：澄清，不创建资料任务
  → 查询交回原工具；资料目标进入原队列/固定执行/逐格校验/XLSX
```

首轮、纠正、独立复核共用 **2 次请求上限**。纠正和复核不能各再用一次。供应商客户端同时限制请求数、每次 64 KiB、1200 输出 token、30 秒，SDK 不重试。超时等结果未知直接停止，同 key 不重发。收到一个明确无效的响应后纠正参数，与未知结果重试是两种行为。

普通查询不再因旧解析器返回了“看似完整”的 route 就跳过理解；明确 `/` 命令、四条精确帮助/概览问句、已有会话选择/回看仍保留快速路径。手动表单、工作台 `use_model=false`、7920 本地模式维持零模型。

`requirements-v1` 保存对象、带来源命名空间的资料字段、保留行规则、目标数量、输出类型、增量操作、正文限制、筛选条件和未解决要求。资料目标在执行前比较此合同，工具计划和工作区ID不参与等价判断。普通查询也有需求投影，但复杂 `analysis_plan` 的逐子句覆盖仍由旧合同验证，尚未迁移成通用语义计划。

## 变更与验证范围

- `tcm/dataops/request_policy.py`：统一策略入口；不能让旧规则偶然命中就绕过模型。
- `tcm/dataops/research_question.py`：机械编译与语义放行分开；明确错误的一次反馈；独立复核不读首轮提案；累计 token、请求数与阶段。
- `tcm/dataops/understanding_contract.py`：需求投影与比较，版本化策略开关。
- `tcm/dataops/service.py`：同一聊天/工作台服务、2次传输预算、策略和源码绑定的幂等回执；目标需求随任务保存。
- `tcm/intent_planner.py`：ETCM“性味”展开为药性与药味，最多12个底层属性字段，与工具层能力一致；药典查询仍最多4字段，防止旧4字段上限迫使四个中文属性漏掉一个底层字段。
- 启动脚本、能力元数据和两页提示同步；旧单次评测器在准备阶段拒绝双请求策略，防止静默超出冻结预算。

本轮测试覆盖两个方向：应接受的陌生筛选提案，以及应拒绝的错误保留行/新增字段提案。另覆盖参数修复、两次耗尽、复核超时、同key重放、429后重试、父子版本和旧文件保持不变。33个受影响模块、303项检查通过，0跳过、0联网尝试；新增V2模块20项。各模块取本轮最终结果，未叠加重复运行次数，见 [离线回归](offline.json)。初次开发测试曾因测试request_key不足8位被接口422拒绝，修正测试输入后通过；未更改接口限制。

[真实来源回放](saved-review.json)：第一轮使用此前 N06 保存的真实模型参数；第二轮为**人工构造的期望复核响应**。实际读取本地甘草/陈皮/大黄资料，返回甘草/大黄两行，5张工作表、128个单元格回读通过。两次 SDK 替身调用、外部请求0；这是集成验证，不是新的模型复核成功率。

## 使用与回滚

7921 使用统一理解策略；7920 保持纯本地。启动示例：

```bash
.venv/bin/python -m scripts.preview_local_tasks \
  --port 7921 --state var/name_resolution_v1/preview-state \
  --rag --research-selection fixed --research-goal-model \
  --understanding-policy unified_v2 \
  --rag-release var/data_releases/r1_names_20261101 \
  --diseases var/disease_catalog_v1/build/diseases.sqlite3
```

网页在 <http://127.0.0.1:7921/>，能力开关可从 `/api/runtime` 的 `dataops.research_selection` 回读，需同时核对 `question_policy`、`question_request_limit` 和 `restart_required`。本次部署验证只作无模型HTTP检查，见 [部署检查](deployment-checks.json)。

回滚时重启相同状态目录，将 `--understanding-policy` 改为 `local_then_one_model_v1`。不迁移或删除数据库、已交付文件。已保存任务继续读原结果；未完成理解回执绑定策略及代码版本，发生冲突应保留原请求记录并新建请求，不静默重发。正在运行的任务应先完成或显式取消，再切换代码。

## 未证明和下一项

- 独立复核仍使用同一模型，只是看不到首轮提案；两个响应可能犯同一个错误。`independent_model_agreement` 是一致性证据，不是正确性证明。
- 无法确认语义时仍会澄清。普通查询只有机械校验，复杂计划仍受旧语法合同限制；没有实现任意任务编排或全局语义验证。
- 旧 `compile_draft` 和显式 legacy 策略保留历史行为，不能单独当作安全执行入口。新策略必须经 `request_proposal` 完整检查后才能入队。
- 本轮新增真实模型请求0，原新题首测5/6及其他历史分数不变；没有新的泛化率、多轮Agent收益、Docker或Langfuse服务端验收。
- 下一项是另行冻结统一策略的真实对照：合法提案误拒率、错误提案误放行率、最终交付、澄清比例、纠正/复核增益、总请求数/token/耗时分别统计；对照旧单次策略。开发反例和保存提案不计作未见保留题。先验证理解质量，再优化静态Prompt开销。
