## 操作与观察

同一新会话按顺序输入：

| 操作 | 验收要求 | 实际结果 |
|---|---|---|
| 你能做什么 | 只介绍当前正式问答范围 | 通过；未推荐候选工作台和收藏 |
| 我想了解茯苓的信息 | 记住药名并询问具体字段 | 通过；要求补充字段，不执行未指定查询 |
| 给出性味和剂量 | 继承茯苓；性味用ETCM，用量用药典；同一药名一张卡 | 通过；返回3个来源字段、合并显示性味和用量 |
| 归经呢 | 继续继承茯苓，不重复索要药名 | 通过 |
| 查询泽泻的ETCM药用部位和药典功能与主治。 | 切换对象并保留显式来源，合并展示 | 通过 |
| 分别告诉我茯苓和泽泻的性味。 | 两个对象均返回，分别合并药性与药味 | 通过 |
| 刷新页面 | 最新及之前各轮答案可回看，不重新提交 | 最新轮恢复通过，新增POST为0；**早期答案只剩摘要，未通过完整回看要求** |
| 白术有哪些成分 | 显示来源关系数量、当前页和翻页 | 首次返回20条/共307条；补充会话点击下一页仍为20条，页码2，总数不变，两页来源行ID无重叠 |

补充会话输入“查询茯苓的性味和剂量”，展开“出处与详细记录”→药典字段出处→字段原页，点击“查看原页”，实际取得PNG并显示；点击证据导出取得Markdown。原页和导出均通过。没有将药典摘录审核状态改为已审核。

独立回读了8个ETCM字段的原始JSON指针与文件摘要、2段药典索引文本与证据位置，均与响应一致。这里验证的是来源一致性，不是药材身份、OCR全文或医学事实的人工审核。

## 唯一确认的产品缺口

连续查询几轮后刷新，最近一轮有完整卡片，早期的性味、用量和归经变为“查询完成，共N项；完整结果与出处已保存。”，无法直接在原轮次回看答案。

- `app.py::conversation()`只取`snapshot.messages[-1]`的`answer_delivery_key`，返回一个`answer_delivery`。
- `templates/index.html`会话加载逻辑将早期消息当作纯文本，只为最后交付恢复结构化卡片。
- 原完整答案仍在独立实例的`dataops/answer_deliveries.sqlite3`；已逐请求键核对保存结果仍在。因此是恢复展示缺口，不是模型理解失败或资料丢失。

下一项最小修复应限定为：按当前保留消息中的交付键恢复各轮保存结果，绑定原消息位置；使用现有会话归属检查，读取失败给出该轮提示，不重新执行查询、不重新调用模型。不能把旧卡片重复附加到最后一轮。

修复验收：连续完成上述字段追问和跨来源查询后刷新，各轮仍可查看原答案及出处；最新轮不重复；表格/澄清后不把旧查询当作新答案；恢复不新增POST或模型调用；会话之间不能访问彼此交付。此修复**本轮尚未实施**。
