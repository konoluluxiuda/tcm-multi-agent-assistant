# 医疗 Agent 框架复用检验

检验日期：2026-10-09。当前提交：`fa27cd0`，包含现有未提交修改。
对比基线：本地 `upstream/main`，`dee00a4`；未拉取远端最新源码。

## 结论

值得复用“文档解析 → 检索 → 重排 → 基于证据回答”的设计和部分组件接口。
不建议直接沿用整套多 Agent 应用改名上线，也没有证据证明多 Agent 编排优于简单 RAG。
推荐以当前仓库为参考，收缩为可测试的文本证据问答核心，再逐步加入中草药领域功能。
本次没有修改业务代码、数据库或密钥，也没有进行新的远程模型调用。

## 方法与边界

- 阅读并对比业务代码与上游本地基线；路由、guardrails、重排、向量存储、联网模块及 app.py 与该基线无差异。
- 对 24 个业务/评测 Python 文件进行 AST 语法检查，全部通过；这不等于依赖或运行检查通过。
- 用 SQLite 只读连接检查当前 Qdrant 文件：34 条 points，`PRAGMA quick_check` 返回 `ok`。
- 当前 Qdrant metadata 与配置维度均为 1024；没有验证每条向量的生成模型或做向量语义验证。
- 运行 `python audits/check_framework.py`：通过 AST 提取真实源码方法，绕过第三方依赖导入及构造器，注入可控模型输出。这些是确定性行为探针，不是端到端测试，不反映模型准确率。
- 重新分析历史 `data/eval/report.json`，没有把历史结果当作此次重跑结果。
- 当前 WSL 无法调用 Docker，localhost:8000 无法连接；宿主 Python 缺少 langchain_core、qdrant_client、torch、docling、pytest。没有安装整套依赖或修改 Docker 环境。容器运行状态和真实 API 连通性未验证。

## 本次可重复的结果

详细输出见 `framework_checks.json`，运行脚本为 `check_framework.py`。

| 探针 | 观察结果 | 含义 |
|---|---|---|
| 单章节含 2400 个英文词，模型返回合法分割点 | 仍输出一个 2400 词块 | 256–512 词只存在于提示词中，没有硬约束；配置的 chunk_size/overlap 没有被切块流程使用 |
| 模型按提示词的另一种说法仅返回 `0, 1` | 标记符连同全文进入单一块 | 分割响应格式要求矛盾、解析不健壮 |
| 合法 `split_after: 0, 1` | 正确得到 alpha、beta 两段 | 正向控制通过，正常格式下基本分割可用 |
| 注入 combined_score 为 -3 和 4 | confidence 原样返回 -3 和 4 | 该值不是经过校准的正确概率；本测试不声称线上模型实际产生了这两个值 |
| 引用输入包含 page=12、doc_id=chunk-1 | 输出仅保留 title、path | 即使输入提供定位，来源输出也丢失定位信息 |
| 注入重排模型异常 | 返回 list，而正常调用方要求二元 tuple | 降级路径会解包失败，或在恰有两项时误解包为两个字典 |
| 参考与回答同为“中草药来源核对” | keyword_recall=0 | 当前英文正则评测不能直接迁移到中文 |
| 历史 11 条异常记录 | rag_confidence 均为 null | 无法判断直接去了搜索，还是 RAG 后搜索失败；评测记录丢失中间路径 |

前六项问题中，切块、分数、引用与重排问题在上游业务代码中已存在；中文评测问题属于新增 eval_rag.py。

## 代码审查确认的其他阻碍

1. `agents/agent_decision.py` 固定 thread_id 为 1；app.py 的 session_id 未传入执行层。
2. 路由提示同时要求无图走聊天、医学问题走 RAG；模型行为不稳定有代码依据。
3. `agents/guardrails/local_guardrails.py` 禁止询问来源、DOI、方法、结果，不适合证据问答产品。
4. `TavilySearchResults` 在 try 外构造；没有密钥时搜索入口直接抛异常。Tavily 不是 RAG 必需依赖，但目前没有完整关闭路径。
5. 每次 RAG 请求新建 MedicalRAG，重新构造重排组件、本地 Qdrant 客户端等；没有清晰的共享生命周期和关闭管理，并发访问待验证。
6. 脑肿瘤节点是占位文本；“人工验证”没有构成真实审核流；CV 模型在模块导入阶段加载，使文本功能依赖无关模型文件。
7. max_context_length 未在回答生成流程实施；长文档切块和提示词大小没有可靠预算。
8. 新 doc_parser.py 关闭页面图片，但表格 get_image(...).save(...) 未做空值处理；是否触发取决于 Docling 返回对象，需在容器用含表格 PDF 验证。
9. 新 eval_rag.py 的 --verify 只以维度决定成功；QA 生成依据截取 4000 字符，judge 证据只有 1500 字符。

## 技术复用决策

| 部分 | 建议 | 复用条件 |
|---|---|---|
| Chat/Embedding 工厂函数 | 保留 | 校验必需配置、超时与服务端参数兼容性；记录模型版本 |
| Docling 文本/表格解析入口 | 保留候选 | 对目标中文 PDF、扫描页、表格做样本验收，保留来源页码 |
| Qdrant 检索接口 | 保留候选 | 管理客户端生命周期、向量模型版本、幂等入库；并发部署方式另行验证 |
| 稀疏+稠密检索 | 做对照后决定 | 不能凭现有英文论文结果推断中文药名检索效果 |
| CrossEncoder 重排接口 | 保留候选 | 修复异常返回并用中文领域问题验证实际增益；不直接平均异构分数 |
| LangGraph | 可选保留 | 流程需要明确状态、条件分支时使用；当前节点数本身不证明价值 |
| 多 Agent 动态路由、通用 query expansion | 首轮移出关键路径 | 先建立简单 RAG 基线，之后按可测收益逐一恢复 |
| 图像诊断、语音、Tavily、当前人工确认流程 | 默认禁用 | 需要时以独立可选模块加入，不阻塞文本问答 |
| 当前 guardrails 和 eval 指标 | 重写 | 与领域目标一致；对中文、来源、拒答和错误分别计量 |

## 中草药迁移时需要新增的结构

以下为数据/软件设计建议，不是经本次测试验证的领域性能结论，也不是临床规则。

- 药材实体使用稳定 ID；保留规范名称、别名、基原、药用部位及炮制信息，不能仅靠文本相似度自动合并同名/近名实体。
- 证据记录原文件、版本/日期、页码/章节、片段原文、来源类型；分别呈现传统记载、实验研究及其他证据，避免混成单一结论。
- 对剂量/单位、禁忌、相互作用、适用对象等问题保留完整限定语；查询扩展不能随意替换实体或适用条件。
- 首轮定位为资料检索与证据说明，不把目前的文件命中率解释为处方或诊断能力。

## 下一轮值得做的验收

在运行环境恢复后，以同一批人工核对的中文问题比较：直接聊天、简单 RAG、RAG+重排、完整路由流程。
先用 30–50 条问题做工程筛查，覆盖别名/歧义、跨资料比较、表格、无答案、追问、请求来源；样本量不足以声称广泛可靠性。

分别记录：真实证据片段 Recall@k、关键结论支持情况、引用定位正确性、适当拒答、实体混淆、错误率、p50/p95 延迟和调用成本。
对不同用户并发、缺少可选密钥、模型超时、空库、重排失败、重复导入增加集成用例。
是否保留多 Agent 应由这些对照结果决定；在这些测试完成之前，仅能给出“设计部分值得复用、整套系统未达到可靠应用状态”的结论。
