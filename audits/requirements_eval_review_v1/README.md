## 1. P1：CLI execute 不能实际执行

位置：`scripts/eval_requirements_generalization.py:130–146,167–179`。

`execute()` 要求注入实现 `run(scenario, policy)` 的 client，但项目没有在该脚本构建真实客户端；CLI 调用不传 client，即使设置 `--authorize-execute` 也报 `execute requires an HTTP client`。现阶段没有 API 初始化、策略进程隔离、父子会话、查询提案执行、任务轮询、产物下载和观察结果标准化实现。

修复：落实 R/G/V 实际配置，接入聊天/工作台真实 API 与同一固定执行器；完成原始响应→观察结果的转换。以真实 ASGI + 模拟 provider + 合成数据库测试 CLI 与 API 路径，不能继续只用 `client.run` 返回参考答案。

## 2. P1：预算错误且未在请求发送前强制执行

位置：同文件 `_budget()`、`execute()`。

预算按场景数而非 turn 数计算。当前 43 场景中 H041–H043 各两轮，因此是 **46 次提交，R=0、G≤46、V≤92、合计≤138**。这仅是完整执行的理论上限，不是新增授权；先前 129 是少算，不应直接发起扩额调用。

此外预算只写入 protocol，execute 没有 provider dispatch 预约、计数或预算拦截。文本 `stopping` 不会自动实现停止策略。`--authorize-execute` 只是启动开关，不是可核验的协议范围。

修复：在实际 provider 边界按场景/轮次/策略持久化预算占用，收到返回后追加回执；区分派发、收到响应、已知 token 和未知用量。纠错/复核共享 V 的两次额度。注入第三次调用，证明在发送前拒绝；超时与 HTTP 失败触发冻结停止条件。

## 3. P1：冻结、重放与中断保存不成立

位置：同文件 `prepare()`、`dry_run()`、`execute()`、`_save()`。

- prepare 写了问题 hash，但 dry-run/execute 都不比较当前问题文件 hash。修改冻结问题后仍执行三组。
- execute 不检查 `_code_hashes()`，评测脚本自身变更未被该门禁拒绝。dry-run 的该检查不能替代 execute 的检查。
- `source_manifest_sha256` 是应用源码 allowlist hash，不是数据库或 release 内容 hash；当前协议未固定数据内容、名称目录及实际模型配置。
- execute 全部结束后才 `_save` 结果，第二组中断会丢失第一组已完成结果。
- 重复 execute 会重新执行所有组合，`write_text` 覆盖结果文件；只有 prepare 拒绝目录重用，不等于执行回执追加且不覆盖。
- 后缀 `.jsonl` 的输出实际是多行 JSON 数组，与输入 reader 的 JSONL 行格式不同，后续接入工具易混淆。

修复：统一单一冻结验证器，在 dry-run/execute/score 校验实际使用输入；冻结数据/依赖/提示词/schema/评分器。实现持久化组合状态与逐次追加 journal，未知状态不可自动重发；明确续跑仅未开始组合。JSONL 应每行一个对象，或统一改名为 `.json`。

验收：题目、参考、执行脚本、数据任意变动都会在模型派发前拒绝；中断后保留首项回执；再次调用不会重跑；不能以重写 manifest“修复”已开始实验。

## 4. P1：评分器能接受不存在的产物与错证据

位置：`tcm/evaluation/requirements_benchmark.py:144–215`。

已复现：

- 两对象需要同一字段，仅提供一个无对象归属的字段可同时满足二者（`(None, ns, name)` 回退）。
- SourceAssertion 的 namespace/name 未参与匹配；值只需出现在整个响应文本，不必来自匹配的来源记录。错误字段和错误值仍可通过。
- `missing_assertions` 完全未评分。
- 两轮任务只给一个 t1 结果，照样通过；没有核对 turn ID/完整轮次/父步骤成功。
- 表格只检查 `artifact_sha256 is not None`，传 `not-a-hash` 且没有任何文件仍通过；不检查表内容、行策略、数量、父字段或旧文件未改变。
- 表格新 hash 不等于旧 hash，只能说明字符串不同，不能证明旧文件完整。
- `http_status=503` 但自报 terminal_state 成功仍通过。该问题与真实 HTTP 映射未实现叠加，会放大假成功。

关系需求还是自由 dict 与普通字段比较，缺少整组关系对象与实际记录匹配；没有通用的来源版本验证。上述内容不能靠在期望字段里补常量解决。

修复：类型化需求与观察，逐对象/关系组绑定结果；实际文件重新打开读取单元格；保存执行前后父文件 hash；对具体对象+字段+来源的值与证据联合断言；校验场景 ID、轮次顺序、终态与 HTTP 一致性。结果必须来自业务返回与文件，不能来自期望答案复制。

## 5. P1：dry-run 43/43 只是参考答案自检；计分分母可缩小

位置：`scripts/eval_requirements_generalization.py:86–101,110–127,150–164`。

`_reference_result()` 将 expected 的对象、字段、证据文字直接填入结果，并生成全零 artifact hash；dry-run 只判断这份复制结果能否匹配原参考。可保留为 reference self-check，但不能称 API 或执行器 dry-run，更不能用它证明真实数据事实已核验。

`score_run()` 只统计已有记录：只留一项 R 的成功结果，仍输出 R 1/1，不报告缺失 G/V；没有完整笛卡尔组合检查，未分离支持任务与边界任务。现有单测反而断言将二者合并为 completed 2/2。

修复：另加通过 ASGI 全链的离线演练，模拟 SDK 但执行真实业务工具。按冻结场景×策略创建完整分母，缺失/父失败列 not_run；重复或未知组合拒绝。分别统计支持完成、边界处理、澄清与未运行。评分器用故意删字段、错来源、错关系组及破坏真实 XLSX 验证能抓住错误。
