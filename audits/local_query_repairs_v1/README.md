# 本地属性路由与普通查询失败提示（2026-11-01）

在旧7920进程复现用户提供的两条失败问句，修复后更新7920/7921并验证。未调用外部模型，未修改名称目录、药典索引和旧评测分数。

## 原因与修复

| 问题 | 原因与处理 |
|---|---|
| `想知道连翘的药用部位` | 字段契约已经能提取连翘，但早期直接查询入口只接受多个属性，单属性落入后面的药典关键词路由。单、多属性现在共用完整契约及唯一候选读取，无需模型或后台排队 |
| `查看白术的药用部位、科名、性味、归经` | ETCM别名缺少性味，整个字段单元未通过。性味现在展开为药性`properties`和药味`flavors`，加上药用部位、科名、归经，共5个存储字段，避免漏掉“味” |
| 普通查询缺少失败原因 | 药材/药典工具增加白名单`failure`；执行后的主聊天查询在顶层和对应`tcm`/`research`中返回同一结构，诊断增加`query_failure`事件 |

`药用部位→origin`在药典中属于合法来源段查询，不能全局删除；本轮修正的是来源路由。单问“性味/归经”保持药典路径，指定ETCM或与科名、药用部位等组合时读取ETCM。显式`/research`仍是药典工具，未扩展其全部口语语法。代词追问保留会话来源，炮制品、提取物名称不截成母药，额外未知任务不被丢弃。

`request_interpretation.herb=""`是通用词法查询中合法的中间值，本身不能证明药名漏提取。只有名称守卫实际拒绝上下文时才返回`name_boundary_unresolved`；目录未命中、字段未记录另行区分。单候选待确认不会误称多个来源。

## 使用与限制

入口：[7920本地](http://127.0.0.1:7920/)、[7921一次理解](http://127.0.0.1:7921/)。直接输入上述原句即可，完整来源保留，中文名关联仍是候选，不等于完成身份人审。

失败结构示例：

```json
{"failure":{"code":"field_not_recorded","stage":"field_resolution","message":"当前来源未检出所需字段；未检出不表示不存在。","automatic_retry":false}}
```

HTTP成功返回不等于字段均存在，调用方应结合工具`status`、字段`state`、`failure`和证据判断。原HTTP/业务状态保持兼容；缺失字段不由模型填造。本轮结构覆盖普通药材/药典查询，不声称所有鉴权拒绝、RAG及异步任务错误都有相同顶层结构。
