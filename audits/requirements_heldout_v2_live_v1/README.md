## 原因已核实到阶段

### V：模型可见契约与宿主约束脱节

六份已收工具调用均在 `delivery.form=answer` 时填写 `row_policy=keep_all`。本地回放 `RequirementsDraftV2.model_validate`，均得到 `answer delivery cannot carry row_policy/count`。尚未进入数据库查询，因此不是数据不足或工具执行失败。

这个条件目前由Python `model_validator`施加，JSON Schema只有可空row_policy字段，没有把answer与table做判别联合。系统提示强调keep_all等表格策略，但未明确answer必须省略row_policy/count。

更关键的是实际纠错请求只发送 `requirements_schema_failed`、`path=[delivery]`、`type=value_error`及代码文件行号/hash，没有发送“answer不得有row_policy/count”的可操作错误说明。模型第二次重复同一错误。有6份原始响应与诊断证据，不能归因于抽象的“模型能力不够”。

字段名还出现中文“科/药用部位”，但被delivery错误更早拦截；是否继续触发字段规范化失败尚未实测，不能把推测计为已验证根因。

### R/G：规则和来源策略仍可能抢占语义

R在第一题没有命中能力路由，第三/四题在 `name_resolution` 的 `name_boundary_unresolved` 拒绝。G对这三题一次理解后完成真实检索与出处交付，证明在这几个表达上模型理解有实际增益。

第二题G选ETCM属性后，被 `query_coverage.validate_query_fields` 的 `query_routed_to_wrong_tool` 拒绝：本地语义保护要求药典性味与归经。这里存在来源默认策略冲突，不能仅靠增加药名同义词修复。

### 评测自身：HV2-02参考过窄

原句没有写ETCM或药典。作者意图及预先标注选择ETCM，但用户可见问句并未排除药典。R返回有来源的药典内容，不能直接判为错误。

原题、原参考、原成绩保持不变，另标注此歧义。后续应在新版本评分契约中支持可接受来源集合，或将“明确要求ETCM”的改写放入开发回归；不得事后改题并声称还是原始未见题成绩。

2. 纠错反馈返回稳定错误码、字段路径、允许值和简短修复要求；不要把内部代码行号当作给模型的修复说明。预算仍为最多2次。
