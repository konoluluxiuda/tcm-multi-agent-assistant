# 多轮与并发追加测试

日期：2026-10-09；测试对象：7861 上的发布镜像 8n1eld/medical-assistant:0.1.0，已配置 Tavily。
全部数据为虚构测试内容，使用知识库副本。没有修改业务代码或原始知识库。

## 结果

| 用例 | HTTP | 耗时 | 功能判断 |
|---|---:|---:|---|
| 用户 A 保存虚构编号 HERB-74291 | 200 | 6.96s | 回复“已记住” |
| 用户 A 下一轮询问编号 | 200 | 6.59s | 失败：声称没有告知编号 |
| 用户 B 使用不同 session cookie 询问编号 | 200 | 10.91s | 未回显编号，但不足以证明隔离有效 |
| 两个同时发起的 RAG 请求之一 | 500 | 3.52s | Qdrant 目录被另一个客户端占用 |
| 两个同时发起的 RAG 请求之二 | 200 | 37.83s | RAG 后走联网回退并返回回答 |

原始结果：state_stability_results.json；日志：state_stability_container.log。
并发请求顺序由调度决定，不能解释为固定“第一个请求一定失败”。

## 对多轮失败的受控检查

直接调用镜像里的 LocalGuardrails.check_output，提供：

- 当前问题：询问本次医学学习笔记编号，若未告诉则说不知道。
- 待过滤答案：“这次医学学习笔记的编号是 HERB-74291。”

过滤后实际返回：“我不知道。你没有在本对话中告诉我这次脑肿瘤医学学习笔记的编号，因此我无法仅依据本次对话回答。”

证据见 guardrail_context_probe.json。
这复现了输出过滤步骤在没有历史的情况下改写正确答案的故障机制。
没有捕获实际 HTTP 请求在过滤前的原始回答，因而不把该探针等同于该请求唯一根因；但该步骤本身已确定可破坏多轮结果。
代码中输出过滤只接收当前 input/output，普通对话生成器则会拼接历史。
联网回答生成提示也仅包含当前 query 和搜索结果：历史只用于改写搜索词，不能保证回答阶段理解“刚才回答”。

## 会话隔离不能判为通过

A、B 使用不同 cookie，但后端 process_query 仍使用固定 thread_id=1，app.py 没有把 cookie 传入执行层。
日志中保留前面的其他会话消息；B 没有回显编号可能被同样的输出过滤影响。
因此本次没有观察到编号泄露给 B，但代码和共享历史结构仍不满足用户隔离要求。
应先修复每用户/每会话的状态传递，再用同一测试验收；不能以“B 回答不知道”宣称隔离安全。

## 并发故障

失败响应：Storage folder ./data/qdrant_db is already accessed by another instance of Qdrant client. If you require concurrent access, use Qdrant server instead.

与每次 run_rag_agent 新建 MedicalRAG、VectorStore 每次新建本地 QdrantClient 的实现一致。
配置 Tavily 只修复搜索密钥问题，不能修复初始化阶段的数据库锁冲突。
后续需根据部署范围选择进程内共享且正确管理的客户端，或使用服务端 Qdrant；同时定义同一会话并发策略。
本次未实施上述修复。

## 综合结论

新增实测阻碍：多轮答案可能被过滤器改坏；并发知识问答可直接 500。
已有来源 URL 写死端口的问题仍未修改，避免重复消耗模型请求，沿用上一轮直接 URL 检查证据。
不能把当前镜像标记为稳定的多用户知识问答版本。
建议下一轮停止堆叠更多功能测试，先修复会话标识传递、输出过滤的上下文、Qdrant 客户端生命周期和引用链接，然后重跑这些固定回归用例。
