## 页面操作

打开 http://127.0.0.1:7877/research-tasks ，使用“计划与澄清验证”。选择“只核对来源关系”，勾选“原请求还包含示例丙草”和/或“原请求还要求药用部位并排表”，点击“创建计划任务”。页面显示完整请求和未覆盖项，工具动作保持0。

直接点“确认并继续”会拒绝执行。只有核对当前显示的执行对象与目标，并勾选“我同意仅执行当前选定范围；未覆盖项继续保留为未完成”后才继续查来源；来源、靶点仍需分别选择。完成后显示“确认范围已完成；原请求未完成”，第三对象和药用部位表留在缺口及下载报告中。未勾选额外请求且范围完整时，维持正常来源查询，不要求额外缩小范围确认。

这些选项声明软件测试需求，不会新增第三药材的查询能力，也不向模型或联网服务发送资料。药用部位在其他聊天工具中可查询，但当前计划工具不支持该并排表，不能用别的入口能力冒充本任务已完成。

## 数据与调用契约

- `request_scope`使用严格的RequestScope版本1，含用户声明的entities、deliverables、synthetic_only与user_declared来源。合成请求可表达甲/乙/丙三对象，可执行TaskPlan仍仅支持甲/乙两味。
- `tcm/request_coverage.py`按任务保存的清单与当前计划计算未覆盖项、额外对象/任务和是否允许执行。客户端不能提交complete、can_execute等覆盖结果，服务端每次重新计算。
- evidence_review包含来源核查这个前置步骤；source_relations只覆盖来源关系。研究任务退为来源查询属于缩小范围；来源任务增加研究核查属于扩大范围，不能用缩小范围确认授权。
- 清单未指定主目标时，用户明确选择的intent填入effective_request；original_request仍保留原始待确认状态。额外请求不会因此被擦除。
- 选择计划时通过严格布尔字段accept_reduced_scope确认。确认记录绑定完整计划和effective_request，计划变化后不能复用；原清单保持不变。

服务端在计划确认、来源/靶点选择、调度前和工具执行前检查覆盖。超出请求的计划、未明确接受的缩小范围会停止，失败不修改已保存任务或版本。所有者、同站请求与revision约束继续沿用；过期确认409，非法范围422。勾选不能扩大权限，不能代替其他浏览器所有者确认。

POST `/api/research/tasks`沿用`mode=synthetic_plan`，增加可选request_scope。新页面始终发送声明清单；调用方也可显式传入。模型提案适配器create_proposal新增可选request_scope，用独立用户声明核对模型输出。

## 完成口径

| 字段 | 含义 |
|---|---|
| confirmed_scope_complete | 当前确认执行的范围完成 |
| original_request_complete | 确认范围完成且没有原请求未覆盖项 |
| report.complete / task.status | 对带request_scope任务按原请求整体判定；缩小范围后子任务完成仍为partial |
| report.gaps | 既有证据缺口，加未覆盖对象和交付 |
| request_coverage / scope_acceptance | 原清单、解决待确认项后的清单、未覆盖项和绑定具体计划的确认 |

页面、JSON和Markdown使用同一服务端结果，报告保留原请求与确认范围；GET/刷新/导出不重新执行或升级状态。空交集可以完成本次查询，但不会填平未处理的第三对象或额外交付。范围全部覆盖而研究证据不足时，也仍为partial。

## 问句入口：先核对请求清单再规划（2026-10-21）

7877任务页新增“合成问句入口”。例如输入“示例甲草和示例乙草有哪些共同靶点？还要药用部位并排表。”，点击“生成待核对清单”。原文只存本地任务库，最大400字符；没有网页模型调用，也不读取药典或ETCM资料。

```mermaid
flowchart LR
    Q[本地合成问句] --> D[waiting_request 原请求清单草稿]
    D -->|用户核对全部对象与要求| P[waiting_plan 可执行计划]
    P -->|范围完整或明确同意缩小范围| S[waiting_sources 确认来源]
    S --> T[waiting_targets 选择靶点]
    T --> R[报告：确认清单及未完成项]
```

### 操作与实际能力

1. 对照原问句检查对象和交付项，取消误识别项，补选漏掉的对象；其他要求每行一项，最多6项、每项120字。
2. 勾选“我已对照原问句核对并修订清单”，提交后才生成可执行计划。至少确认两个合成对象及一项要求；不会把代词自动补成甲乙两味。
3. 再确认执行计划。第三对象、药用部位表、手填其他要求仍未覆盖时，须明确同意只执行选定范围；只勾清单完整不等于接受缩小范围。
4. 按已有流程确认来源和靶点。报告显示“确认清单全部完成”，未覆盖项持续保留；下载包含原问句、自动草稿、用户核对及计划。

自动草稿只是固定目录的字面匹配建议，不处理否定、代词或任意领域实体。例如“不要看研究记录”仍可能勾选研究记录，界面明确要求人工纠正；不会将其称为语义识别成功。本轮未扩充失败题规则或模型提示词。

其他要求被当作未支持的交付保留，不交给模型编写答案。只有其他要求、没有支持交付时，不能把它替换成一个未请求的共同靶点任务。界面中的草稿修订提交前不自动保存；确认提交后，原文、原草稿、修订清单和revision持久保留。

清单允许用户修正自动建议，修订是用户的需求声明。API的original_request_complete在本入口指用户核对后的声明清单完成；不是对原问句全部语义的自动验证。报告明确保留`raw_question_completeness_automatically_verified=false`，界面使用“确认清单全部完成”避免混淆。删除建议项和补充要求均可从草稿与确认清单对照追溯，原文不被改写。

### 接口、存储与兼容

`tcm/task_request.py`生成本地草稿及原文锚点，不调用规划器、模型或资料工具。`POST /api/research/tasks`新增`mode=synthetic_question`和question，创建waiting_request任务；不能同时提交plan/request_scope绕过审核。GET、列表、刷新和导出不重新提取或运行工具。

`POST /api/research/tasks/{id}/request`携带revision、严格RequestScope和`confirm_complete=true`完成核对。RequestScope新增可选other_requirements；服务端保存`request_draft`和`request_review`，由确认后的清单生成有界TaskPlan，再停在waiting_plan。旧choose/resume不能略过waiting_request；已确认清单不能用该接口再次覆盖，修改需求须新建任务。

权限、同站检查、revision冲突和SQLite持久化继续复用现有机制。执行前核对确认记录与当前清单，清单被改动后不能沿用旧确认。旧范围确认缺少新增可选空字段时会先规范化比较，不因默认空列表的引入而失效；真正新增要求仍使旧范围确认失效。

原结构化计划、旧合成任务、ETCM本地任务和旧CLI模型原型保留原入口及含义。该新闭环尚未迁移到真实ETCM查询；没有账号、通用语义提取、MCP或新的LangGraph checkpoint功能。
