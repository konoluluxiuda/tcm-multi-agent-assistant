## 目的与范围

原A/B/C候选仍保留。为避免只测工具恢复、没有测业务完成度，本轮建立双侧属性、药典字段与共同靶点的统一验收夹具。

执行两个对照：

- `flat_reference`：顺序调用两侧文本与结构化查询，再计算共同靶点；这是确定性平铺参照，不是A的生产模型循环。
- `existing_subgraphs`：实际调用现有 `run_pair_report` 与嵌套 `run_report` LangGraph图；这是C的子流程技术基线，不是模型主管自主委派。

两者使用同一份临时SQLite和药典检索索引，实际执行 `text_search`、`structured_search` 与 `shared_targets`。无预设正常工具结果、无模型替身生成答案。缺失字段与不可用来源是显式故障注入。药典文本和出处元数据均是合成夹具，不代表核验真实PDF。

这一轮是业务协议的前置验收，不是完整A/C选型，更没有据此淘汰B。

共4个固定开发变体、8次执行。2次满足全部请求，2次出现相对于请求的错误完成标记；另外4次是故意注入缺失/故障后的合理partial。不能把2/8作为泛化成功率，也不能把脚本的passed解释成全部业务通过。

具体缺口：夹具有23个不同共同UniProt标识，现有报告只返回20项首页。报告自身scope声明为首页，但用户问“全部”时仍可能得到complete。因此底层首页契约可用，并不表示上层完整请求得到满足。新增验收器独立核对请求覆盖，能够识别这一差异。

返回的ETCM共同靶点见证行均通过原JSON路径与文件哈希核对；文本字段检查存在性和合成出处。没有对自然语言结论做质量评审，没有测性能收益、token费用或真实模型自主规划。

本轮测试：新增验收器4项＋已有两药报告/持久化12项，共16项通过。

## 对选型的影响

1. 现有图已经具备独立子流程与汇总依赖，不应把它包装成新完成的多Agent创新。
2. 调整执行拓扑并未自动增加需求覆盖。A/B/C都必须采用同一外部验收器，不能用各自返回的complete作为成功标准。
3. 模型主管仍有待验证：只有在动态分解、选择合适子任务和处理缺失等任务上带来收益，才有证据支持引入；本轮没有对其收益作结论。
4. 下一阶段应让A模型循环和C主管适配器使用这些相同底层工具、相同总预算与完成条件。先固定SDK替身检查调用协议，再以另行授权的合成真实模型对照检验自主规划。B同样可接入此工具协议，不能被本轮结果排除。

正式候选验收前应解决“全部”需求：支持分页汇总，或明确返回partial及缺少的页；不能简单把所有首页报告改为partial，也不能仅放宽验收。当前按隔离审查范围只记录问题，没有修改生产行为。
