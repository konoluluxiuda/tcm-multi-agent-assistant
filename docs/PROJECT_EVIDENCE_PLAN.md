# TCM 项目：用实验留下能力证据

日期：2026-10-12。本文是实施计划，不代表新增评测已经完成。

## 1. 问题与当前交付边界

面向中草药资料查询与科研辅助，先解决“在不补造缺失信息的条件下，查到正确记录，并让每个字段能回到原始来源”。本地 ETCM2.0 快照存在名称缺口、重复来源、稀疏字段及靶点身份错配；因此先做药材基础信息，不直接把全部 JSON 向量化，也不将未核验关系作为事实。

目前已经交付 2,076 份药材基础记录的独立查询 API/页面：支持来源 ID、拼音/拉丁/英文名查询、字段子串 AND 筛选、比较、歧义候选和字段定位。中文名映射暂缓；药材查询尚未接入原医疗聊天；中文 RAG、文献报告和持久记忆不能作为已有成果。

框架是否值得保留，要分任务验证：精确查询先看直接工具是否足够；多步骤、分支和状态恢复任务再比较 LangGraph 编排。Agent 数量、SDK 导入成功和模型能回复，都不作为业务价值证据。

## 2. 已有证据与尚未证明的能力

| 已有证据 | 支持的结论 | 不能推出的结论 |
|---|---|---|
| [数据审计](ETCM2_DATA_AUDIT.md) | 已识别本地文件规模、药材字段缺口和部分数据质量问题 | 全库科学内容正确或关系可直接使用 |
| [固定候选集](../eval/README.md)：数据层/API 各 30/30 | 冻结快照下，选定工程契约与来源预期相符 | 真实用户任务成功率 100%、中文问答准确率；人工签核仍待完成 |
| [来源访问验收](../audits/source_access/report.md)：38 项回归、87 项 HTTP 检查 | 已覆盖本轮访问控制与上传隔离分支 | 生产容量、账户级鉴权、端到端研究任务可用性 |
| [轻量部署验收](../audits/docker_recovery_2026-10-12.md) | 独立药材服务可以在本地 Docker 运行 | 已发布新镜像或可支持某个生产并发量 |

记录数、测试数、HTTP 检查数和真实任务数分别报告，不相加成为“准确率”。源字段对照是来源一致性检查，不是药理结论验证。

## 3. 建立 60 条任务候选，而不是凑 60 条断言

先围绕当前可运行入口收集问题；自然语言任务明确标记为规划能力。以下配额是目标，不是已有真实问题数量。

| 任务类型 | 目标数量 | 成功标准 |
|---|---:|---|
| 定位药材并读取指定字段 | 15 | 定位正确来源，字段与原文一致，缺失明确 |
| 多条件筛选及分页查阅 | 10 | 条件全部生效，集合、计数、分页正确 |
| 指定药材属性比较 | 10 | 对象和字段正确，每项可定位，无补造 |
| 同名、未知名称和暂未支持的中文名 | 10 | 返回正确候选或明确限制，不任选、不猜测 |
| 稀疏数据、缺失文献与证据范围 | 10 | 缺失不等于无研究，传统属性不冒充现代研究证据 |
| 用户修改条件、追问来源的连续任务 | 5 | 在明确的产品交互中完成；尚未实现时标记未支持 |

问题优先来自实际查阅记录、使用者访谈或用户提供的需求；研究者设计题标为 `designed`，真实使用题标为 `observed`。合成或设计题不能改写成真实用户题。问题、用户目标、操作入口、预期状态、正确记录/字段/定位、来源版本、审核状态都需要保存。

候选题先独立读取源数据建立预期，再由人类审核；不能从被测系统输出反推答案。不要复制现有 30 个契约测试、换几个药名后宣称完成真实任务评测。保留现有 v1 冻结集及签核状态，新任务集另行版本管理。

在调参前按实体与意图分组划分开发集 20 条、保留测试集 40 条，避免同一药材同义改写跨组泄漏。小样本报告分子/分母和类别分布，不宣称统计显著性。未支持任务单列，并同时报告覆盖率和支持范围内成功率，避免只选容易题。

## 4. 对照实验按依赖推进

| 阶段 | 比较什么 | 先具备什么 | 如何决策 |
|---|---|---|---|
| 当前 M1 | 人工查原 JSON 与现有结构化页面/API | 同一任务、快照；人工耗时另行实测 | 是否更容易查准、查出处；不把直接查询伪装成 Agent 增益 |
| M2 检索 | 字段感知文本与固定长度切块；dense 与 dense+BM25 | 已审核相关片段/字段标签；中文题依赖可靠名称处理 | Recall@k、MRR/nDCG、误召回类型及耗时 |
| M2 重排 | 不重排、现有模型、多语言候选 | 固定相同候选集合与题集 | 正确证据排序收益能否抵消延迟/内存成本 |
| 聊天集成后 | 直接工具、简单 RAG、按需工作流 | 相同问题可由各方案处理，统一证据和错误契约 | 任务成功、引用与预算；按任务类别选择方案 |

固定代码提交、数据/索引指纹、模型与嵌入版本、提示词、检索参数、上下文预算和运行环境；冷启动与预热后的测量分开。一次只改一组因素，失败与超时也保留。重复运行的次数和随机参数写入实验计划；没有同条件基线，不写“提升”。

## 5. 指标与原始记录

| 指标 | 口径 |
|---|---|
| 任务完成率 | 满足题目全部必需条件的任务数 / 该范围全部任务数；超时和失败计入分母，未运行另报 |
| 能力覆盖率 | 当前可支持的任务数 / 完整目标集任务数；明确哪些入口还未实现 |
| 引用正确性 | 分开统计定位可解析率与“关键结论确被引用内容支持”的比例；缺引用计失败，源数据真实性另审 |
| 拒答/降级 | 应拒答或澄清的题中正确处理比例；同时记录对可回答题的错误拒答 |
| 延迟 | 请求起止实测；均值、p50、p95，并列样本量、并发、冷/热状态和超时数 |
| 调用成本 | 记录每次模型/工具调用、token 用量、缓存信息；按运行日价格计算并注明币种/价格来源，未知值为 null |
| 失败分布 | 实体混淆、漏条件、检索遗漏、错误引用、无依据补造、上下文截断、工具失败、会话错误分别计数 |

纯 SQLite 查询没有模型 API 调用费用；这不等于机器、人工、外部工具或整个系统成本为零。不可用 token 不能填成 0。成本数据未实测前保持空缺。

每条运行记录至少包含 `run_id`、`case_id`、方案、提交/数据/模型版本、预期及实际状态、耗时、工具调用、证据 ID/字段定位、错误类别、审核结果和成本状态。原始回答按需要脱敏保存；不要提交密钥、用户私有资料或整份原数据。汇总报告必须能追溯到逐题记录。

## 6. 主动制造失败，检查兜底是否有效

确定性工程故障使用替身或临时数据，不修改原快照，不调用付费 API。业务失败再在冻结题集验证。

- 实体：同名不同来源、未知药名、未支持中文名；要求澄清或明确限制。
- 证据：缺字段、无 PMID、检索到相关但不支持结论的片段；不补造，不把空结果当无研究。
- 工具：超时、429、空响应、畸形响应、存储不可用；错误与正常无结果分开，重试必须受预算限制。
- 上下文：大量返回记录、长历史、关键条件在早期消息；记录截断策略和丢失条件，不静默给出完整性承诺。
- 隔离与版本：跨会话追问、服务重启、索引与数据版本不匹配；分别验证所有权、记忆边界和阻断逻辑。

每次修复留下一条“触发输入 → 修复前现象 → 根因 → 改动 → 同题复测 → 未解决限制”。修复后保留原失败记录，不能删除难题来提高通过率。

## 7. 后续任务与成果表达

- [ ] EV-01（随 M0-06）：把不依赖私有快照/付费服务的回归接入 CI；本地全快照验收单独标注，不静默跳过后报告全通过。
- [ ] EV-02（M1-06）：已于2026-10-15设计60条AI候选并通过650个来源锚点校验，全部designed、observed=0；人工签核、真实使用题收集及逐题执行仍待完成。见 [候选说明](TCM_TASK_CANDIDATES.md)。
- [ ] EV-03（M1/M5-01）：先给现有轻量 API 建逐题耗时/状态报告；保留真实失败，不提前实现全套 tracing 平台。
- [ ] EV-04（M2）：冻结对照方案与分组，运行检索/重排实验；聊天集成后才评测完整 Agent 增益。
- [ ] EV-05（M5-06）：从原始记录整理项目说明、代表性失败和未解决问题。

当前顺序仍是 M0-06 离线 CI，随后推动人工签核和任务集；无需为了项目描述新增框架或立即接入更多服务。

项目经历写成：“面向【用户与任务】，在【数据、算力、权限与成本约束】下负责【可证明的个人工作】；比较【实际运行的方案】，依据【同条件实验】选择【方案】；在【版本、题数、审核方式】下测得【原始记录支持的指标】，发现【失败类型】，完成【修复】，仍存在【限制】。”

现阶段可如实描述：完成 ETCM2.0 本地数据审计，围绕 2,076 份药材基础记录构建可溯源的结构化查询 MVP；固定 30 项工程候选用例在数据层和 API 层均通过，人工签核待完成。不能改写成“中文中草药 Agent 准确率 100%”或“多 Agent 显著优于 RAG”。
