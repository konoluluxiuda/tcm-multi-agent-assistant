## 项目怎么介绍

**中草药资料问答系统｜Python、FastAPI、SQLite、可选模型工具调用**

基于开源 Multi-Agent-Medical-Assistant 改造，面向多来源资料核对，完成自然语言字段查询、连续追问、来源约束和可回查答案。不能声称从零研发整个框架；以下表述应由本人复现、理解后选择使用。

- 统一字段与来源规则，支持单药、多药和跨来源查询；对模型生成的需求检查对象与字段覆盖，缺项保留，避免静默换源。
- 补齐澄清轮次的对象上下文和后续字段继承，将结构化答案与对话摘要分别保存，使保留窗口内的历史答案和出处可恢复。
- 接入有界的需求提取与工具反馈纠正，采用固定来源工具执行；模型不能凭输出“完成”绕过程序校验，也不负责改写来源事实。
- 建立请求诊断、回归和部署核验，保留失败证据，区分离线工程检查、已见题回放和真实模型效果。

## 90 秒讲解稿

“我在一个开源医疗助手基础上，收敛出中草药资料问答系统。使用场景是学生或资料整理者核对药材字段，例如先说药名，再追问性味和用量。性味默认来自 ETCM，用量来自药典，必须把对象、字段和来源对应起来，还要能回查原文。

实际遇到过三个问题：澄清后丢失药名，模型把合理请求解析出来却被下游拒绝，以及刷新后早期字段答案只剩摘要。我分别补齐会话对象范围、统一字段来源规则、分开保存摘要和结构化答案。程序负责查资料和约束交付，前端按药材合并展示；模型只在启用时理解需求、根据工具反馈纠正，不自由编造资料。

工程侧已有离线回归和真实资料浏览器走查，上一版 Docker 也验证了恢复。随后一次真实模型小样本中，四场景通过三项；连续追问因为上下文准备规则没识别新表述而失败，随后修复并做了离线回归，没有重跑模型刷分。它说明已见模板通过不能代表泛化。项目还没有真实客户和生产规模数据，也不证明药典抽取全部正确。”

## 面试追问：为何没有堆更多技术

**为什么用模型，不能全写规则？** 明确模板适合本地解析，变体表达可以受益于模型理解。当前 W 允许工具检查后的纠正与需求复核，执行仍固定。历史已见题中 W 有收益也有过度澄清；最新小样本为 3/4，失败发生在宿主上下文准备，不能说增加模型调用必然解决问题。

**为什么没有 Vue、Redis 或多 Agent？** 当前是单机资料查询，既有页面和 SQLite 已承担展示、会话及请求状态。Vue 可在交互规模明显增大时评估；Redis 可在多进程共享状态、队列吞吐或延迟有实测瓶颈时评估；多 Agent 需要可分解且独立验收的任务与实测收益。现在都没有这样的采用依据，不能把暂未需要说成这些技术没有价值。

**RAG、向量检索和重排在哪里？** 当前明确字段主要用结构化读取与药典索引摘录。BM25、BGE/Qdrant、RRF 有[独立实验](RAG_RETRIEVAL_COMPARISON.md)，不能全部列作聊天必经路径。先说明查询类型和证据，再讨论召回、重排；不把历史小样本无增益外推为向量检索永远无用。

**LangGraph 和 Agent Loop 在哪里？** 仓库历史任务执行有 LangGraph；常规问答不需要全部走图。当前值得讲的是有界模型理解、只读工具反馈、宿主校验和保存结果。native 自选工具循环属于实验，不作为已完成产品能力。

**为什么不让模型整理最终答案？** 已暴露问题主要是同药重复、证据展开过多和公式显示，确定性整理已能解决。再加一次生成会引入事实漂移和成本；只有用户确有跨段归纳需求、且有证据支持性验收时再评估。
