## 2. 要解决的问题与本轮范围

### 2.1 根因定位

当前路径大致为：

```text
问句 → 本地路由 / 模型输出 ResearchDraft 或 QueryIntent
     → 多处读取原句，重新判定对象、字段、行策略和工具
     → 编译成 ResearchGoal 或查询/分析计划
     → 工具执行 → 结果与证据
     → Requirements 摘要（部分路径，不能统一约束执行）
```

模型正确理解后，可能被另一套局部语法误拒；模型漏掉要求时，也可能因为校验只覆盖部分字段而放行。增加提示词可以改善第一步，但不能修复后面的契约分裂。

本轮目标路径：

```text
请求 / 所有权 / 幂等 / 安全边界
  → 需求提取（模型或完整本地适配器）
  → RequirementsDraftV2
  → 语义一致性判定 + 宿主名称绑定
  → BoundRequirementsV2
  → 能力解析 + 参数校验 + 完整覆盖检查
  → CompiledPlan / ResearchGoal
  → 现有执行器
  → 按需求核对结果、缺失和证据
  → 响应 / XLSX / 可回读诊断
```

模型负责理解需求；程序负责把确定的需求映射到受约束的工具。这一阶段改善的是**理解与规划契约**。它不会自动证明动态 Agent 比固定工作流更有效，也不要求本轮引入新的主管、多 Agent 或 MCP 服务。

### 2.2 必须覆盖的业务

- 单药属性、多字段属性、药典字段、跨来源字段查询。
- 多药分别查字段，严格区分每个对象的要求。
- 成分/靶点来源记录与共同靶点等已支持查询的兼容性。
- 指定药材的表格核对、保留全部、筛选齐全、限定数量。
- 基于父工作区追加字段，保留对象、旧字段、旧文件及来源版本。
- 能力、数据概览、数据库介绍等不需要药名的请求继续可用。

不要求本轮新增：治疗推荐、疾病用药预测、成分靶点预测、语义记忆、数据库迁移、新检索算法或关系数据导出格式。

暂未迁移的分析功能必须列出清单，保留显式 legacy 入口。复合问句若混合新旧路径且没有完整计划，返回具体澄清；不能只执行支持的部分。禁止在新路径失败后自动再调用旧模型链。

## 4. U1：先定义契约，不能直接开改提示词

### 4.1 模型草稿与宿主绑定必须分开

建议新策略名称 `requirements_v3`，新契约标识 `requirements-v2`。策略版本与数据结构版本是不同概念。**这两个值目前未实现，不能现在就拿来启动服务。**

草稿采用严格 Pydantic 模型，`extra='forbid'`，使用判别联合限制不同需求类型。建议包括：

| 字段 | 约束 |
|---|---|
| `version` | 固定 `requirements-v2` |
| `status` | `ready` / `needs_input`；needs_input 不得执行 |
| `operation` | `new` / `append_fields` |
| `objects` | `{ref, mention}`；ref 仅为本提案内部引用，不是数据库 ID；查询类、表格类分别受现有上限约束 |
| `requirements` | 带唯一 `id` 的类型化需求；逐对象字段、关系查询或数据集级需求，不能一个全局字段集合覆盖所有对象 |
| `delivery` | answer/table；table 才有行策略、完整性条件、数量等；不能把临床排序藏在 top_n 中 |
| `unresolved` | 非空即不入队，保留不能解释的原始要求 |

逐对象字段需求建议形如：`{id, kind:'read_fields', object_refs, fields:[{namespace,name}]}`。关系需求另用明确的 `kind`、对象数、关系类型和完整性范围；不能把关系塞进普通属性字段。

**结构示例**（这是建议契约示例，不是当前 API 请求体）：

```json
{
  "version": "requirements-v2",
  "status": "ready",
  "operation": "new",
  "objects": [{"ref": "o1", "mention": "黄芪"}],
  "requirements": [
    {"id": "r1", "kind": "read_fields", "object_refs": ["o1"], "fields": [{"namespace": "etcm", "name": "medicinal_part"}]},
    {"id": "r2", "kind": "read_fields", "object_refs": ["o1"], "fields": [{"namespace": "pharmacopoeia", "name": "功能与主治"}]}
  ],
  "delivery": {"form": "answer", "include_evidence": true},
  "unresolved": []
}
```

宿主负责生成绑定结果：本地名称候选、已选来源、数据版本、所有权、父工作区 ID/版本、身份状态。模型不能提交 `identity_verified=true`、已批准来源 ID、文件路径或权限。唯一中文名候选可用于查询，不等于跨库药材身份已审核。

不带药名的数据库介绍/概览使用数据集级需求，允许 `objects=[]`；不能统一加“必须有药名”的限制导致旧问题复发。

### 4.2 行策略、顺序与默认字段

- `keep_all`：所有指定对象保留；缺值保留为空/缺失，不自动筛掉。
- `filter_complete`：当前明确候选池内保留满足完整性规则的全部记录。现有引擎最多 5 个明确候选，不得默默放宽成全库筛选。
- `top_n`：最多返回指定数量的合格记录；当前目标数量 1–5，候选池最多 20。无排序依据时采用明确的稳定候选顺序，不声称药效优劣。
- 其他查询不需要行策略，不能强填 `keep_all` 冒充筛选承诺。
- 保留用户对象/字段顺序；集合排序只能用于语义比较或签名，不能改变用户要求的交付顺序。
- 区分“用户要求列”“系统附带出处/标识列”和“完整性筛选列”。默认附带列不能无声改变用户的筛选要求。若现有 ResearchGoal 无法表达该区分，应明确报表达缺口，或单独做兼容扩展并测试；不能在适配时悄悄改变语义。
- 追加字段只扩展字段集合；对象、候选池、行策略、来源版本不能在 append 中改变。扩展后仍符合现有字段上限，否则澄清，不截断。

### 4.3 v1 兼容

历史 Requirements 中 `fields` 在 query 路径没有稳定命名空间，部分早期 row_policy 值也不能直接等同新契约。旧记录继续按原始元数据展示；信息不足时标记 legacy projection，不推测为可重新执行的 v2。

不批量重写旧状态库。新任务写版本，新回读按版本分派；无版本旧记录采用明确 legacy 阅读器。为旧已完成任务、未执行提案、父子工作区各保留一个兼容 fixture。

**U1 验收**：严格 schema、未知键、对象引用、重复需求 ID、数据集无药名、父版本及历史记录阅读均有测试；此时不改变默认服务路径。

## 5. U2：补全能力矩阵，生成不读原句的计划

### 5.1 先核对当前清单的缺口

不能直接把现有 `CAPABILITIES` 当成完整真值。至少核对：

| 差异 | 当前事实 | 处理 |
|---|---|---|
| ETCM 字段 | DataOps 表格 11 个；业务查询 12 个，额外有 `reference_pmids` | 从契约枚举生成/核对，不把只读字段误标为表格能力 |
| 药典字段 | 表格 7 个；业务查询 11 个，额外含性状/鉴别/检查/含量测定 | 按交付形式分别注册，保持现有字段数上限 |
| 关系命名 | 清单用 ingredients/targets/common_targets；工具参数使用 ingredient/target 等 | 设置唯一内部枚举与显式适配，不多处各自替换字符串 |
| 两药报告 | `PairArgs` 恰好两药，有字段、属性、all_targets 和成本约束 | 不能仅凭某字段允许 pair_report 就允许任意对象数/组合 |
| 分页与全量 | 成分/靶点记录每页 20；全量共同靶点有特定路径 | 注册分页/完整性能力，不把第一页标成全部 |
| 可用性 | 字段支持、数据源未启用、字段缺失是不同状态 | 分别记录 static capability / runtime availability / result evidence |

每个能力项至少提供：稳定 capability ID、字段/关系、支持形式、对应实际工具或交付编译器、对象数范围、参数模型、运行依赖、成本/分页约束。注册到不存在的工具应在测试中失败。不要维护第二份会漂移的工具参数 schema。

### 5.2 推荐的纯函数边界

```python
# 建议接口，不是现有函数
bind_requirements(draft, catalog_snapshot, parent_metadata) -> BoundRequirementsV2
validate_requirements(bound, capability_snapshot, runtime_limits) -> ValidationResult
compile_plan(bound, capability_snapshot, parent_metadata) -> CompiledPlan
validate_plan_coverage(bound, plan) -> CoverageResult
```

后三个接口不接收 `question`，也不得从全局状态/闭包取原句。权限、名称候选合法性等宿主约束仍要做；“不读原句”只限定机械编译器，不是禁止安全边界和语义阶段理解用户。

`CompiledPlan` 每一步保存：step ID、真实工具名/类型化参数、覆盖的需求 ID 与对象/字段、依赖、成本、结果完整性条件。由宿主绑定真实来源 ID，不让模型自由编造。

映射例子：

| 需求 | 计划 |
|---|---|
| 黄芪药用部位＋功效 | `herb_attributes` 读取 medicinal_part；`pharmacopoeia_lookup` 读取功能与主治，两条需求均有覆盖 |
| 山药、茯苓各自成分与靶点 | 逐药逐关系调用 `herb_relation_records`，共四个覆盖块；明确当前分页，不冒充读取全部 |
| 白术科名，黄芪功效 | 白术属性＋黄芪药典；不能给黄芪科名就算满足白术需求 |
| 两药药典对比＋全部共同靶点 | 条件满足时复用 `pair_evidence_report`；all_targets 由需求完整性要求推导，计入叶子调用预算 |
| 指定药材整理功效/注意成表 | 编译现有 ResearchGoal 并调用现有交付流程；不新写 XLSX 引擎 |
| 将成分列表放入普通字段表 | 若现有表格契约不支持，返回 unsupported_delivery 并说明支持查询；不能丢列生成成功表格 |

覆盖必须按 `(requirement_id, object_ref, namespace, field/relation, scope)` 检查。不能只比较工具个数或全局字段并集。同一字段来自错误药材、错误来源、错误分页范围都不能算完成。

对语义相同的需求可以合并调用，但保留每条需求映射；每一个步骤也必须有需求或必要依赖来源，禁止偷偷添加无关工具。全部计划在执行前校验，不能先执行前半段再发现后半段不支持。

**U2 验收**：用固定绑定契约直接测试计划，不调用模型；原句如何改写都不影响相同契约的计划。通过注入删除步骤、调换药名/命名空间、减少范围、超预算验证完整性守卫。

## 6. U3：接入模型与新策略，保留语义责任边界

### 6.1 提示词与工具定义

新路径向模型提供一个需求提交工具（例如 `submit_requirements_v2`），不让它同时在 ResearchDraft、QueryIntent、新契约三套工具之间选。

输入包括当前问句、允许的名称候选、能力说明、字段规范、父需求摘要（追加时）和少量合成正反例。理解任务不需要药典全文、ETCM 记录或整个会话；该限制是本阶段输入最小化设计，不代表恢复此前已取消的资料外发禁令。

提示词必须明确：

1. 完整保留对象、逐对象字段、排除项、数量、行策略和交付形式；未知要求进入 unresolved。
2. “作用”映射药典功能与主治不能被全量属性替代；但真正歧义要澄清，不假装所有词都有唯一含义。
3. “整理所有对象”与“只留齐全”不同；“增加”不能删旧字段或换对象。
4. 不发明药名、数据 ID、权限、验证状态；数据不存在与工具不支持不同。
5. 数据库介绍不需要药名；不支持的复合要求不能静默删去。

提示词版本、工具 schema SHA256、能力快照版本均进入诊断。模型输出严格解析一次；不使用不受控 JSON 修补或未计费的第二客户端。

### 6.2 两次请求预算如何使用

复用当前 `configured_model` 和真实 HTTP 次数预算。新策略初期保持每次提交最多 2 次请求，SDK 自动重试关闭：

- 首轮结构有效且有完整本地语义依据：记录依据，再机械规划；“识别到一个关键词”不算完整依据。
- 首轮结构有效但无完整语义依据：剩余一次用于独立提取/复核。复核者看到原句、允许能力和上下文，不看第一次答案；逐对象规范化比较。
- 首轮收到明确、可修复的 schema/参数错误：剩余一次用于纠错；如果纠错后仍需要额外语义复核而预算已耗尽，返回澄清，不能偷偷第三次请求。
- 传输结果未知：停止并保留原回执，不自动重试；同 key 不重新计费。
- 两次提案不一致、存在 unresolved、范围/权限不允许、能力不支持：具体澄清或拒绝，不无限纠错。

两次提取一致只证明一致性，不证明正确。因此真实未见问句评测仍然必要。

当前 `query_coverage` 和 `validate_question` 的语义保护不能通过全局关开关删除。新路径应将它们负责的含义检查移到语义阶段，并在机械阶段用新契约覆盖检查接替；旧路径继续使用旧检查。测试要证明新执行器没有再次调用旧原句计划验证器。

特别注意：一个结构合法但错解“全部保留”为“只留齐全”的草稿，机械校验本来无法知道它错了。该用例必须由语义测试拒绝；不能因为机械层成功就删除反例，更不能让机械层重新藏进正则。

### 6.3 保留本地模式

`use_model=False`、精确控制命令和部署模型关闭仍保证零外部请求。新策略的本地适配器仅在完整理解时生成同一契约；不完整时具体澄清，保留用户原句。明确命令可保留现有执行路径，记录 route_basis，不能把本地模式伪装成模型驱动。

**U3 验收**：SDK 替身覆盖接受、纠错、复核分歧、预算耗尽、未知派发、无模型模式；调用次数、费用/token 统计与原始回执一致。

## 7. U4：打通请求、恢复和诊断

### 7.1 幂等不能被新策略破坏

继续复用 `RequestJournal`：先 reserve，再可能发模型请求；已得到的提案先 complete，再尝试入队。

签名除了现有请求体、来源、父版本、模型/接收方、旧代码指纹，还应包含新契约版本/指纹、能力快照、规划器、提示词/工具定义版本、新语义策略。已完成任务按原版本回看；未执行提案遇输入或配置变化应冲突，不能使用同 key 重新付费解释。

必要生命周期测试：

- 首次成功→同 key 重放：新增请求数 0，工作区/结果一致。
- 提案成功、队列忙 429→同 key 重试：复用已付费提案并正常入队，不能生成无意义 failed 工作区。
- 模型派发未知→同 key：保持未知/冲突，不重新派发。
- 父 revision、数据源、策略或能力版本变更：相应冲突可解释，不覆盖旧文件。
- 进程重新创建 service 后继续读取回执和交付；恢复语义沿用当前状态机，不自行承诺 exactly-once 执行。
- 不同 owner 不能读/执行对方任务、绑定来源或诊断。

### 7.2 诊断与用户反馈

复用现有 X-Request-ID 和 Langfuse 关联，建议新增/细化阶段：

```text
requirements_extract → requirements_schema → semantic_check
→ object_binding → capability_resolution → plan_compile
→ plan_coverage → execution → delivery_verification
```

每个阶段记录 status、code、契约/策略版本及必要摘要；计划记录 step_id/requirement_ids/tool，不存模型隐藏思维过程。若 Langfuse 不可用，本地诊断仍可回读。

失败响应至少在既有兼容位置保留 `{code, stage, message}`，并关联 request_id。建议稳定错误码：`requirements_unresolved`、`semantic_disagreement`、`object_ambiguous`、`unsupported_delivery`、`capability_unavailable`、`plan_requirement_omitted`、`parent_revision_conflict`、`model_dispatch_unknown`；能复用既有码的优先复用，最终映射写入测试。

用户主答复先给结果或具体缺口，不倾倒契约与审计细节。例如“成分可以查询，当前表格暂不支持成分列表；尚未创建任务。”数据筛选 0 命中应说明“0 条满足条件”和排除原因，不能只有空表。

保留调用计数口径：本次新增 provider requests、任务累计请求、内部决策步数分开。帮助快路径当前用 `assistant.llm_calls`，不要编写假设所有响应顶层都有 model_calls 的测试。若统一字段，需同时更新 API 文档和兼容测试。

**U4 验收**：用 ASGI TestClient 跑 chat 与工作台完整链，包含真实 fixture 存储、队列、证据和 XLSX 回读；不只断言 HTTP 200。

## 8. 测试矩阵与执行命令

### 8.1 开发回归最少覆盖这些场景

| 场景 | 必须断言 |
|---|---|
| 黄芪有什么作用 | 药典功能与主治，不能仅 ETCM 属性 |
| 黄芪药用部位和功效 | 两个来源字段都覆盖 |
| 想知道连翘的药用部位 | 正确药名＋ETCM medicinal_part，不是药典来源 |
| 白术药用部位、科名、性味、归经 | 科名/部位/药性/药味/归经，规范字段映射明确 |
| 山药和茯苓各有哪些成分和靶点 | 四个逐对象关系结果，不漏成分 |
| 白术科名、黄芪功效 | 不能交换对象仍算覆盖 |
| 整理白术黄芪功效注意，缺失也保留 | keep_all，缺失不删行 |
| 只留功效注意都有记录的 | filter_complete；0 命中解释原因 |
| 从指定候选中挑两条齐全的 | top_n=2，未达数量真实 partial，不编造补齐 |
| 增加贮藏，保留旧字段 | 新版本字段并集，旧产物哈希不变 |
| 把成分放进普通字段表 | 未支持时明确澄清，不能生成少列“成功”表 |
| 介绍两个数据库 / 当前能做什么 | 无药名也正确；精确帮助零模型 |
| 三味药要求两药专用报告 / 超预算 | 参数/范围错误，工具未派发 |
| 缺字段 / 多候选 / 数据源关闭 | 三种不同原因，不统一报药名错误 |
| 治疗处方、改源文件、工具结果中的指令 | 既有边界有效；资料内容不能改需求/工具权限 |

同义改写与相反含义必须成对：保留↔筛除、追加↔替换、两个↔全部、有值↔允许缺失。不用只改标点的题量充数。

### 8.2 离线命令（当前已存在）

在项目根目录使用 `.venv/bin/python`，不要使用缺依赖的 base Python：

```bash
git status --short
git diff --stat
.venv/bin/python -m scripts.check_understanding_counterexamples --out var/requirements_v3_gate_on.json
# 负对照预期 exit 1；应单独执行并如实记录，不与成功链用 && 串联。
SEMANTIC_REGEX_GUARDS=0 .venv/bin/python -m scripts.check_understanding_counterexamples --out var/requirements_v3_gate_off.json
# 新测试按 tests/test_*.py 命名，标准入口会自动发现。
.venv/bin/python -m scripts.run_offline_ci --out var/requirements_v3_ci
```

用独立输出目录，不覆盖已有审计。标准 CI 已清理供应商配置、禁用 dotenv 加载并阻断网络；临时并行运行也必须复用同等隔离和 worker，不能降低门槛。仅直接调用 `--worker` 不等于自动获得完整环境清理。

验收要求：新测试与既有完整 CI 通过、零跳过、零联网尝试。故意失败的负对照不计入通过项。运行期间源码需稳定；记录运行前后源码快照。测试数增长本身不是完成证明。

### 8.3 真实模型泛化评测另开阶段

实现 Agent 先交付离线结果。随后由另一个未参与修改的 Agent/人工准备 **40 条未见问句**，冻结预期契约与数据快照，不把答案交给模型，不将这批题写回 prompt。

建议构成：字段/跨源 12、逐对象复合 8、表格筛选 8、追加 4、模糊/不支持/边界 4、数据集级 4。按固定来源快照标注可执行、缺数据、应澄清的预期，而不是一律要求执行成功。

比较本地基线、unified_v2、新策略；相同快照、模型、超时、输出上限和每次提交最多 2 请求，不重试。三组可以分阶段运行，不能把一次测试授权或旧剩余额度自动当成整个新实验。

先落盘协议和预算，再按届时有效授权执行。本交接不发起模型调用。模型开关与执行驱动分开记录，不能把固定交付成功写成动态执行收益。

报告指标与分母：

- 契约语义完全正确率：对象、逐对象字段、范围、行策略、输出及 unresolved 全对；单独报告澄清质量。
- 正确契约误拒率 / 错误契约放行率：用独立标注判定，不用两个模型意见一致当金标准。
- 可执行题端到端完成率：需要结果、出处、数量/缺失语义、产物内容全部满足；HTTP 200 不算完成。
- 请求次数、token、延迟；非重放与重放分开。
- 首次失败阶段：理解、名称、参数、能力、规划覆盖、取数、交付；每条关联 request_id 与诊断。

建议预先冻结上线门槛：40 条中整体预期处置至少 36 条正确；支持且可执行题完成率至少 90%；已知静默漏要求、跨对象错配、越权/重复付费回归均 0；新策略端到端完成率不低于 unified_v2。预算最多 2 次必须硬通过。小样本只能作为候选上线证据，不宣称统计上已证明提升；若收益不显著，保留新策略为可选项，报告真实成本与局限。

评测后修复的题转入开发集，后续泛化再使用新冻结题，不能反复调同一批题后宣称未见题通过。

## 9. 上线与回滚

离线通过后先开独立端口、独立状态目录验证新策略，使用当前实际来源配置；不要在文档里填一个尚未存在的数据路径。启动参数应以修改后的 `--help` 为准。

部署检查至少包括 `/api/runtime` 的源码/磁盘一致、实际策略、模型理解开关、执行驱动、需求/能力版本，以及主页、工作台、RAG 页面和零模型帮助请求。需外部模型的测试与纯本地检查分开记录。

回滚以切回旧策略为主，保留所有新任务和证据。旧版本若无法读取新契约，继续用新版本程序的 legacy 策略运行，或将新旧状态目录隔离；不能假定 checkout 旧代码就能读取新状态。活动任务完成或按现有机制取消后再切换，不强杀后声称“已安全恢复”。

默认策略只有在验收完成后才讨论切换。Docker 构建/镜像发布、Git 提交/推送属于独立交付项，不因为本文件存在就视为已授权执行。

## 10. 接手 Agent 最终应提交的材料

1. 实际变更清单、采用的契约和编译接口、兼容保留范围。
2. `audits/requirements_v3/README.md`：实现与未完成项分开，记下真实失败和修正。

4. 至少两条完整示例轨迹：跨源问句→契约→计划→结果；表格追加→父版本检查→新文件→旧文件未改变。
5. 真实模型未运行时显式写 `live_model_evaluated:false`；fixture 结果不得称真实模型准确率。
6. 更新设计文档、用户说明、路线图中的**实际已完成**部分；失败或未覆盖的能力保留，不把 U1–U4 完成等同整个项目完成。
